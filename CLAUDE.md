# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

ares-gameserver is a LostCity rev 274 game server and cache tooling. It packs a LostCity Content checkout into the cache the
stock clients expect and speaks their wire protocol. It is its own source of truth: Engine-TS is no longer a reference.
Depends by path on `../ares-compiler` (script compiler) and `../ares-shared` (script ABI: opcodes, triggers, var
type codes); a change to `ares-shared` must pass both crates' suites.

## Commands

```
cargo run --release                                   # world (ares); packs data/pack on first start
cargo build --release --bins                          # every binary (cargo run builds only ares)
cargo run --release --bin ares-pack -- build          # clean build of data/pack from build.srcDir (default ../content)
cargo run --release --bin ares-pack -- keycheck       # private.pem / public.pem / public/client/client.js agree
cargo test --release                                  # unit tests + every snapshot gate
cargo test --release --test differential vm_corpus    # one gate (one #[test] per gate in tests/differential.rs)
```

After an intentional output change, bless pack snapshots first (other gates load `tests/golden/<case>/data/pack`),
then everything else, then review:

```
BLESS=1 cargo test --release --test differential full_build_matches
BLESS=1 cargo test --release --test differential
git diff tests/
```

`BLESS=all` rewrites every JSON snapshot and must leave `git diff` empty. Never hand-edit a snapshot (except slots a
gate reports as not blessable). Commit inputs and snapshots together. A new gate that passes first time gets a mutation
check (break one expected value, confirm it fails).

Snapshot inputs are generated by Python scripts (run with `python -I`):
- `tools/make_pack_fixtures.py [<Content>]` writes `tests/fixtures/<case>/content/` (text configs and maps authored
  in the script; binary assets copied from `../Content`). Fixtures build with `build.verify=false`. Re-bless after.
- `tools/make_packet_corpus.py`, `tools/make_server_steps.py` for the packet corpus and the `servers_match` steps.

`PACK_STRICT_GZIP=1` makes gzip archive comparisons byte-exact. The `--no-default-features` build drops the
`web-client` feature (axum HTTP/WebSocket).

## The output contract

The project promises **reproducible `data/pack` bytes** for a content tree and **deterministic outbound packet bytes
per tick** for given inputs and seeds. Read `docs/behaviour.md` before touching anything that reaches output: it lists
each rule and the file it lives in. Key points:
- Many JS semantics are kept on purpose: VM maths in `f64` wrapped to int32 (`util::numbers::wrap_f64`), UTF-16 string
  indexing, `Mulberry32` world RNG and shared `JavaRandom`, `linklist` processing order, `indexmap` everywhere order
  reaches output (`serde_json` with `preserve_order`).
- Section C lists deliberate bugs that reach output. Do not fix them.
- Directory walk order drives ids and sector layout (B.1).
- Deliberately not added as deps: `zip`, `byteorder`, `clap`, `image`.

`docs/testing.md` describes every gate, fixture case (`01-minimal` … `07-varo`), the wire replay scenarios
(`tests/replay`, logins answered by `link::login::inline` and every nondeterministic source pinned) and the unit corpora.

## Architecture

`src/lib.rs` has the module map. The big picture:

- **Pack pipeline** (`pack/`): `ares-pack build` and the world's first start / live reload walk Content, parse text
  configs (`pack/parse.rs`, `pack/config/`), compile scripts via `ares_compiler` (`pack/compiler.rs`), build maps,
  sprites, interfaces, models, then write jag archives (`io/jagfile.rs`, bzip2) and the `main_file_cache` FileStream
  (`io/filestream.rs`, gzip archives 1–4) plus `server/*` files for the engine.
- **Engine** (`engine/`): `World` (`engine/world.rs` + `engine/world/*`) loads the pack, and `World::cycle()` runs one
  600 ms tick in fixed phases: world, clients in, NPC event queue, NPCs, players, logouts, logins, zones, info
  (`rsbuf` player/NPC info), clients out, cleanup. Zones (`engine/zone/`) buffer per-tick events; `routefinder/` does
  pathing/collision.
- **Script VM** (`script/`): `provider.rs` loads compiled scripts, `runner.rs` executes, `ops/*` implement opcodes by
  area (player, npc, loc, obj, inv, number, string, …). Opcode numbers and pointer rules come from `ares-shared`.
- **Networking**: `net/` is the game protocol (TCP on `node.port`); `web/` serves `public/` and bridges WebSocket game
  connections. `link/` holds the World's login and friend messages (`LoginLink { Ws, Inline }` in `engine/runtime.rs`; the friend link is an optional WebSocket). The world does not talk to the logger yet.
- **Servers** (`server/`): the login, friend and logger servers (bins `ares-login`, `ares-friend`, `ares-logger`),
  sqlx over SQLite or MySQL with schema in `migrations/{sqlite,mysql}`. With `easyStartup`, `ares` spawns them.

## Running locally

Server root is the repo dir: `data/config/world.json` (optional, all keys defaulted; see README), `data/config/*.pem`
(login RSA key, required, must match the prebuilt `public/client/client.js`), `data/pack/` (generated). Defaults: login
server off, `node.production` off (all players staff 4, `::` commands on), `build.liveReload` on. Web client at
`http://localhost/` (port 80 on Windows/macOS, 8888 on Linux). Dev commands: `::reload`, `::rebuild`, `::serverstats`,
`::tele`, `::~<name>` (runs `[debugproc,<name>]`).
